# 보안길잡이 AI · SecurityAdvisor

2026년 공공 AI 대전환 챌린지 제출작

**반복되는 보안 업무는 자동으로, 담당자 협의까지 편리하게.**

공공기관의 사업 담당자가 기획서와 업무 설명을 입력하면 AI가 보안 서류 작성을 돕고, ICT인프라·정보보안 담당자의 협의와 최종 확정까지 연결합니다. 지원 서류는 **방화벽 정책 허용 신청서**와 **정보화사업 보안성검토 신청서**입니다.

이 저장소는 **2026년 공공 AI 대전환 챌린지 심사·시연을 위한 통합 실행본**입니다. 프론트·백엔드 소스와 DB 실행 구성을 포함하므로 **Docker만 설치하면 전체 서비스를 실행**할 수 있습니다.

## 프로젝트 개요

보안 지식이 부족한 신청자와 전문 담당자 사이의 정보 전달을 지원합니다. 신청자는 사업을 설명하고, 담당자는 필요한 서버·망·보안 정보를 보완하며, 신청자는 변경 내용과 근거를 확인한 후 제출합니다.

**사업 기획서·AI 인터뷰 → ICT인프라·정보보안 협의 → 신청자 최종 검토·제출 → 담당자 최종 확인·서류 확정**

| 영역 | 주요 기능 |
|---|---|
| 신청 작성 | 기획서 첨부·분석, AI 인터뷰·추천 답변, 형식·작성 권한 검증 |
| 담당자 협의 | 서버·통신 구간·운영 정보, AI 구성 제안 비교·선택 적용, 보완·반환·재협의 |
| 최종 검토 | 협의 기준본과 변경 전후 비교, 근거 연결 AI 요약, 최종 초안 수정·확인·제출 |
| 문서·운영 | 제출본 보존, 서버 생성 PDF, 방화벽 적용·적용 불가·회수·연장 기록 |
| 업무 관리 | 담당자 재배정·인계, 알림·처리할 일, 역할별 검색·페이지 조회 |
| 기관 관리 | 질문·기한·지식 게시, 기존 신청 버전 유지, 업무 지표, AI 모델 구성·시험·복원 |

AI 결과는 사람의 확인을 거칩니다. **서류 확정과 실제 장비 적용은 별개**이며, 이 환경은 실제 방화벽 장비를 변경하지 않습니다.

## 설치와 실행

준비물: Docker Desktop(Windows/macOS, Linux 컨테이너 모드) 또는 Docker Engine + Compose v2(Linux), 인터넷 연결, 웹 브라우저. 여유 메모리 8GB·디스크 10GB 이상을 권장합니다. Java·Node.js·PostgreSQL을 별도로 설치할 필요는 없습니다.

제출 저장소의 ZIP 또는 Git 복제로 소스를 받은 뒤 **이 README와 `compose.yaml`이 있는 폴더**에서 실행합니다.

Windows PowerShell:

```powershell
Copy-Item .env.example .env
docker compose up -d --build
```

macOS / Linux:

```bash
cp .env.example .env
docker compose up -d --build
```

기존 `.env`는 덮어쓰지 않습니다. 최초 빌드·이미지 다운로드·모의 데이터 생성에는 수 분 이상 걸릴 수 있습니다.

| 접속 주소 | 용도 |
|---|---|
| [localhost:3000/login](http://localhost:3000/login) | 서비스 로그인 |
| [localhost:8080/actuator/health](http://localhost:8080/actuator/health) | 서버 상태 확인 |
| [localhost:8080/swagger-ui.html](http://localhost:8080/swagger-ui.html) | API 문서 |

```bash
docker compose ps -a
docker compose logs --tail 30 demo
```

`demo` 로그에 `완료: 지정 계정 5개, 사업 14건`이 표시되면 준비 완료입니다. 초기화 작업인 `demo`의 `Exited (0)`은 정상입니다. DB·첨부 문서는 전용 볼륨에 보존되며 재실행해도 기존 시연 진행 상황을 덮어쓰지 않습니다. 포트 충돌 시 `.env`의 `FRONT_PORT`, `BACK_PORT`를 변경합니다.

> 기본 `.env.example`은 **키 없이 실행하는 모의 AI 모드**입니다. 실제 AI 시연은 아래의 실제 AI 설정을 적용하세요. 모의 모드는 고정 응답이며 실제 모델의 분석 성능을 보여주는 모드가 아닙니다.

## 추천 시연 순서

약 10~15분 동안 단계별로 준비된 신청을 이용할 수 있습니다.

1. **안대웅 / 시연 01:** 기획서 첨부·분석 → AI 질문 → 추천 답변 확인·저장.
2. **김도헌 / 시연 03:** 처리할 일 카드 → 서버·망·운영 정보 작성 → 임시 저장·확인 → 협의 완료.
3. **정용석 / 시연 04:** 인프라 협의 결과·보안 체크리스트 검토 → 정보보안 협의 완료.
4. **박소영 / 시연 06:** 변경 전후 비교·AI 협의 요약 → 최종 초안 생성·수정·확인 → 제출.
5. **김도헌 → 정용석 / 시연 07:** 제출본 최종 확인 → 서류 확정 → PDF 다운로드.

## 실제 AI 연결

1. `.env`에서 `LLM_MODE=live`로 설정합니다.
2. 사용할 공급자의 키를 `OPENAI_API_KEY` 또는 `OPENROUTER_API_KEY`에 입력합니다.
3. `docker compose up -d --no-deps app`으로 서버에 반영합니다.
4. 관리자 `moon.sw`로 로그인 → **AI 모델 구성**(`/models`)에서 모델·키 참조·용도·출력 한도·우선순위를 확인하고 연결 시험을 실행합니다.

**키 등록이나 연결 시험 성공만으로 기본 모델이 바뀌지는 않습니다.** 활성 구성 중 키와 허용 호스트 조건을 만족하는 모델을 작은 우선순위 값부터 선택합니다. `apiKeyEnv`에는 키 자체가 아닌 환경변수 이름을 지정합니다.

| 구성 | 실제 검증 모델 | 최대 토큰 | 설정 안내 |
|---|---|---|---|
| OpenAI | `gpt-4o-mini` | 협의 요약 4096 | `openai-default`의 초기값은 1024이므로 문서 용도에 맞춰 조정 |
| OpenRouter | `deepseek/deepseek-v4.1-flash-1017` | 기본 4096 | `OPENROUTER_API_KEY`, 우선순위 5 |
| OpenRouter 문서 전용 | 위 DeepSeek 모델 | 8192 | `openrouter-deepseek-document`, `DOCUMENT`, 우선순위 4 |

이는 2026-11-11 검증 설정입니다. 공급자 계정의 모델 사용 권한이 필요합니다. GPT를 우선 사용하려면 다른 활성 구성보다 작은 우선순위(예: 1)를 지정하세요. 용도는 인터뷰·요약·문서·담당자 질의로 구분되며, 협의 요약과 최종 초안은 `DOCUMENT`를 사용합니다.

키는 `.env`에만 보관하고 저장소에 올리지 않습니다. 다른 PC에는 키가 전달되지 않습니다. 추론 모델은 생각하는 토큰도 출력 한도에 포함하므로 문서용 한도를 충분히 설정해야 합니다. 잘린 응답이나 목록에 없는 근거는 저장하지 않습니다. 연결하지 않는 모델은 비활성화하거나 키를 비워 두세요.

OpenAI 호환 서버를 추가할 때는 `LLM_ALLOWED_HOSTS`에 호스트를 등록하고 앱을 재생성합니다. 별도 모델 서버·가중치는 배포본에 포함하지 않습니다. 외부 모델 호출에는 해당 공급자의 정책과 비용이 적용됩니다.

## 실행 검증

### 설치·업무 흐름 자동 검증

모의 데이터를 수정하기 전에 실행합니다. Java·Node.js 설치가 필요하지 않습니다.

```bash
docker compose --profile test run --rm smoke
```

5개 계정·역할, 권한 차단, 신청 상태, 문서·PDF, 협의 이력, 모델 설정, 신청 생성·입력·첨부·철회를 검사합니다. 모의 모드에서는 모의 AI 흐름도 검사합니다. 검사 후 철회된 자동 점검 신청 1건이 남으며, 실제 AI 모드에서는 유료 모델을 자동 호출하지 않습니다.

### 실제 AI 연동 검증

시연 01이 작성 가능한 상태이고 06이 최종 검토 상태일 때 실행합니다. **모의 데이터를 외부 모델에 전송하며 호출 비용이 발생합니다.**

```bash
docker compose run --rm --no-deps -e DEMO_ORIGIN=http://front:3000 demo node scripts/live-smoke.mjs --confirm-live
```

안대웅 계정의 문서 분석·인터뷰, 박소영 계정의 협의 요약·최종 초안을 검사합니다. 결과는 모의 데이터에 저장되며 자동 확인·제출은 하지 않습니다. 다시 실행하면 첨부·대화가 추가되고 현재 초안이 갱신됩니다. 요약만 검사하려면 `--step=summary`, 최종 초안만 검사하려면 `--step=final`을 명령 끝에 추가합니다.

검증 범위와 실제 모델 결과는 [검증 기록](docs/JUDGE_VALIDATION.md)에 정리했습니다. 자동 검사는 모든 AI 응답의 사실 정확성을 보장하지 않습니다. 소스별 전체 검사는 프론트의 `npm run check`, 백엔드의 `./gradlew check`를 개발 원본 저장소에서 실행합니다.

## 중지·재실행·초기화

데이터를 유지하는 중지·재실행:

```bash
docker compose stop
docker compose up -d
```

**시연 DB·첨부 문서·모든 입력을 삭제하고 처음부터 생성할 때만** 다음 명령을 사용합니다.

```bash
docker compose down -v
docker compose up -d --build
```

명령은 이 배포 폴더에서 실행합니다. 프로젝트 이름은 `security-advisor-demo`입니다. 시연용 계정과 모의 데이터로 구성한 로컬 실행 환경이며 실제 기관 운영 환경과 분리해 사용합니다.

## 문제 해결

| 증상 | 확인 사항 |
|---|---|
| Docker 연결 실패 | Docker 실행 여부·Linux 컨테이너 모드 |

| 로그인 실패 | 아이디·최초 설치 비밀번호, 연속 실패 잠금(기본 15분) |

| 자동 검사 실패 | 시연 중 상태를 변경했는지 확인; 오류 확인 후 필요 시 초기화 |

## 개발부터 통합 배포까지

### 1. 개발 원본에서 수정·검토

Front와 Back은 독립된 개발 저장소입니다. 각 저장소의 최신 main에서 작업 브랜치를 만들고, 아래 검사를 실행한 뒤 변경 요청(MR/PR)에 결과를 기록합니다.

| 변경 | 개발·검증 방법 |
|---|---|
| 화면·입력·프론트 연결 | Front에서 `npm ci`, `npm run dev`로 모의 API 개발 → `npm run check`, `npm run build` |
| 업무 규칙·권한·AI·DB | Back에서 개발 → `./gradlew check`(JDK 25·Docker 필요, Windows는 `gradlew.bat`) |
| 실제 화면·서버 연결 | Back을 실행하고 Front의 `.env.local`에 `API_MODE=api`, `API_BASE_URL`을 지정 → `npm run dev:api` |

API 변경은 **Back의 `docs/api/openapi.yaml` → Front의 `contract/openapi.yaml`·출처 기록·타입·모의 API → 양쪽 연동 검증** 순서로 맞춥니다. DB 변경은 새로운 Flyway 마이그레이션으로 추가하며 이미 배포한 파일을 수정하지 않습니다. 서로 연결된 변경 요청에는 상대 저장소의 요청 링크와 함께 배포해야 할 버전을 적습니다.

### 2. 검증된 버전으로 배포본 갱신

검토·검사가 끝난 원본을 main에 병합하고 새 릴리스 태그를 지정합니다. 그다음 이 저장소에 스냅샷 갱신 변경 요청을 만듭니다. **Front·Back main의 변경은 이 저장소나 실행 중인 Docker에 자동 반영되지 않습니다.**

1. Front·Back에서 배포할 태그와 정확한 커밋을 정합니다. 한쪽만 변경했으면 다른 쪽은 기존 검증 버전을 유지하고 조합을 명시합니다.
2. 해당 커밋의 Git 추적 파일을 `git archive` 등으로 추출해 각각 `front/`, `back/`에 반영합니다. 삭제된 파일도 반영해야 하므로 단순 덮어쓰기 후 옛 파일을 남기지 않습니다.
3. `.git`, 실제 `.env`, API 키, 로컬 DB·첨부 자료, `node_modules`, `.next`, `build` 등 개발 환경 파일은 포함하지 않습니다. 개발용 `.github/`와 공통 규칙 사본의 제외 기준은 [RELEASE.md](RELEASE.md)를 따릅니다. 공통 규칙 9종은 루트에 한 번만 유지합니다.
4. `RELEASE.md`에 원본 저장소·태그·커밋·변경 내용·검증 결과를 기록합니다. `snapshots.json`의 저장소·태그·커밋 및 파일별 해시 목록도 해당 버전의 manifest 형식에 맞춰 추출한 원본 기준으로 갱신합니다. 해시는 SHA-256이며 `.bat` 파일의 CRLF는 LF로 정규화합니다.
5. 아래 검사를 실행하고 결과를 변경 요청에 남깁니다. 통과 후 병합하고 통합 배포 저장소에도 별도의 릴리스 태그를 지정합니다.

GitHub와 공공 GitLab의 배포 버전은 다를 수 있습니다. 이 체크아웃의 정확한 출처는 `RELEASE.md`와 `snapshots.json`을 기준으로 확인합니다.

현재 `scripts/verify-snapshots.py`는 **스냅샷 검증 도구**이며 원본 다운로드나 해시 목록 갱신은 수행하지 않습니다. 해시 목록만 현재 파일에 맞춰 바꿔 검사를 통과시키지 말고, 지정한 원본 커밋에서 추출했는지 먼저 확인합니다.

### 3. 통합 실행 검증

이 저장소 루트에서 실행합니다. Python 3은 스냅샷 검증에만 필요하며 서비스 실행에는 Docker만 필요합니다.

```bash
python3 scripts/verify-snapshots.py
docker compose up -d --build
docker compose ps -a
docker compose --profile test run --rm smoke
```

Windows에서는 `python3` 대신 설치된 Python 3 실행 명령을 사용합니다. 자동 업무 검사는 초기 상태의 모의 데이터를 전제로 하므로 **기존 시연 데이터를 초기화하지 말고 별도 검증 환경**에서 실행합니다. 같은 PC에서 분리할 때는 `docker compose -p security-advisor-release-check ...`를 모든 명령에 일관되게 사용하고 `.env`의 `FRONT_PORT`·`BACK_PORT`도 겹치지 않게 설정합니다. 기존 환경과 같은 프로젝트 이름을 사용하면 데이터를 공유하게 됩니다.

실제 AI를 수정했다면 [실제 AI 연동 검증](#실제-ai-연동-검증)도 수행합니다. GitLab 업로드 보안 검사 통과는 빌드·업무 흐름 검증을 대신하지 않습니다. 기존 `.github/workflows/`는 GitHub용 설정으로, GitLab에서 동일한 CI가 자동 실행된다고 가정하지 않습니다.

### 4. 기존 설치에 업데이트

DB와 첨부 문서 볼륨을 백업하고 현재 배포 커밋을 기록합니다. 설치 폴더의 미커밋 변경을 확인한 뒤 승인된 배포 버전을 받습니다. main 기준 업데이트 예시는 다음과 같습니다.

```bash
git pull --ff-only origin main
docker compose up -d --build
docker compose ps -a
```

기존 `.env`와 데이터 볼륨을 유지합니다. 새 환경변수는 `.env.example`과 비교해 필요한 항목만 추가합니다. 업데이트에 `docker compose down -v`를 사용하면 데이터가 삭제됩니다. 업데이트 후 로그인·신청 조회·변경 기능을 확인합니다. DB 마이그레이션이 적용된 경우 코드만 이전 버전으로 돌려도 복구된다고 보장할 수 없으므로 백업과 마이그레이션 호환성을 함께 확인합니다.

상세 협업 기준은 [CONTRIBUTING.md](CONTRIBUTING.md), 현재 배포 출처는 [RELEASE.md](RELEASE.md)를 확인하세요. 스냅샷 폴더 내부 README는 해당 릴리스 시점의 원본이며 최신 개발 안내는 각 개발 저장소 README가 기준입니다.
